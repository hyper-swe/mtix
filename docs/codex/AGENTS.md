# AGENTS.md — mtix Integration

The project briefing is root `MTIX.md`, fully regenerated by `mtix docs generate`. Native root `CLAUDE.md` and `AGENTS.md` contain mtix pointers alongside user content. Valid mtix marker blocks migrate without changing other user bytes; malformed pairs are refused. `HYPERSWE.md` suppresses new pointers and absent native-file creation, while existing pointers remain. Reference files in `.mtix/docs/` keep their existing `--force` behavior. `MTIX.md` defaults to tracked. Every generation run checks all existing root `CLAUDE.md` and `AGENTS.md` files, including unchanged pointers. If all are ignored or locally excluded, mtix adds one marked block (`# mtix: managed local briefing` followed by `/MTIX.md`) to Git’s local `info/exclude`, including Git worktrees. Any tracked or otherwise non-ignored pointer, or no pointer files, removes only that mtix-owned block. All user and unmarked exclude rules survive byte-for-byte, including a missing final newline. If a user rule still ignores `MTIX.md` when a pointer is tracked, generation prints a one-line notice. No Git repository means no exclude write. The committed `.gitignore` is never edited for `MTIX.md`.

Nonempty agent IDs and assignees must fit in 64 UTF-8 bytes and must not be whitespace-only or contain control or invisible format characters (including bidi controls and zero-width characters). Accepted raw values are preserved unchanged. An empty create assignee means no explicit assignment: parent auto-claim still applies when enabled: the child is claimed for the parent's assignee only when the creator is that assignee, otherwise it is created open and unassigned. Set `MTIX_AUTHOR_ID` or the `author_id` config key to the agent that claimed the parent to inherit its claim on create or decompose. With no supplied or configured author, the child stays open and unassigned even if the recorded creator (`cli` on the CLI or `mcp` on MCP) matches the parent’s assignee. A present empty update assignee clears the assignment; omission preserves it. Claim requires an agent ID. Unclaim acts as the given agent. The CLI uses `--agent`, else `MTIX_AUTHOR_ID`, else the `author_id` config key; MCP uses `agent_id`, with the same fallbacks; REST requires the `X-Agent-ID` header and returns 400 without it; gRPC has no fallback and needs the agent in the request. It is refused when no agent is set. Only the assignee can release a claim unless force is given. This check is a coordination guard on a self-asserted identity (any caller can name the assignee), not authorization. These checks apply to existing CLI, REST, gRPC and MCP inputs; they do not rewrite historical imported or synchronized identities.

mtix is an AI-native micro issue manager. It provides hierarchical task
decomposition with dot-notation context chains for LLM agents.

## Setup

```bash
# Install mtix (choose one)
brew install hyper-swe/tap/mtix
# or download from https://github.com/hyper-swe/mtix/releases

# Initialize in your project
cd /path/to/your/project
mtix init --prefix PROJ
```

## Task Workflow

### 1. Find Work

```bash
mtix ready              # List tasks available for pickup
mtix list --status open  # All open tasks
```

### 2. Read Context

```bash
mtix context PROJ-1.2.3  # Assembled briefing from root to this task
```

The context chain traverses from root to leaf, combining every ancestor's
description into a single prompt. This is your complete briefing — read it
fully before starting.

### 3. Claim and Execute

```bash
mtix claim PROJ-1.2.3 --agent codex
# ... do the work ...
mtix done PROJ-1.2.3
```

### 4. Create Tasks for New Work

Every change needs a task — even one-line fixes:

```bash
mtix create "Fix null validation in CreateNode" \
  --description "Why this task exists" \
  --prompt "Exact files and functions to modify" \
  --acceptance "Testable criteria that define done"
```

`mtix create --type` and `mtix update --type` set work classification (bug, feature, task, chore, refactor, test, doc). Update omission preserves; `--type=` clears. `mtix show` and `mtix list` display the hierarchy tier as **Node type** and the work classification as **Issue type** (`node_type` and `issue_type` in JSON). `mtix list --type` filters hierarchy (epic, story, issue, micro); use `mtix list --issue-type bug` to find bugs. Existing unclassified nodes remain unset.

### 5. Decompose Large Tasks

```bash
mtix create "Subtask title" --under PROJ-1 \
  --description "..." --prompt "..." --acceptance "..."
```

### 6. Export State

```bash
mtix export --board-only > .mtix/tasks.json  # Refresh the journal-free board mirror
```

## Sharing a ticket link

To point a person at a ticket, run `mtix url <id>` (for example `mtix url MTIX-12.3`; add `--json` for `{"id", "url"}`). It prints the link that opens that ticket's full detail (prompt, annotations, acceptance) in the web UI, and the link survives reload and back/forward in the browser. It needs a running `mtix serve` for this project: with none running it prints nothing on stdout and exits non-zero naming `mtix serve`, so start the server (or ask the user to) and run it again; an unknown id fails with not found. The command contacts no remote service and never needs a credential. Never put a token in a URL.

## Rules

1. **Always read the context chain** before starting work (`mtix context <id>`)
2. **Never skip task creation** — every change must be tracked
3. **Report blockers** with `mtix comment <id> "blocked: reason"`
4. **Run `mtix export --board-only > .mtix/tasks.json`** before committing — include tasks.json in your commit

## Waiting for inbox events

An optional background park is `mtix inbox --agent <agent-id> --wait --timeout 0`:
zero has no limit, and already pending events return even if the initial
database lookup outlasts a positive timeout. That lookup remains interruptible
by caller cancellation (CLI SIGINT or SIGTERM). After an empty lookup, waiting
for new events uses only the remaining timeout budget measured from entry.
Events mean exit 0; an empty positive timeout means exit 5; SIGINT or SIGTERM
means exit 7.
A negative timeout is refused. Keep foreground waits within the harness's tool
limits; use an indefinite park only where background tasks are supported. Handle
and ack events explicitly before parking again.

For MCP `mtix_inbox_wait`, explicit `timeout_seconds=0` waits without a limit
until an event or caller cancellation. Omission uses default 60 seconds;
positive values are capped at 60 seconds, and negative values are refused.
Cancellation is an error, and an empty positive timeout returns `[]`.

## Health diagnostics

Plain `mtix doctor` preserves operator-local files, including stale attach shims
and records. Use `mtix doctor --fix` for registered shim and glue repairs;
other commands retain automatic attach refresh.

An operator-local flush failure can follow publication of a complete record:
preserve its files and surface the I/O error to the operator. Read-only
`mtix hooks status --json` checks placement and access; it does not prove
power-loss durability or undo a published write. The admin skill explains
per-OS flush behavior and recovery.

## Trust and grants

Registered local-only ids are implicitly wakeable unless denied. Hub/relay ids require operator-local confirmation: use `mtix agent allow dev` at a terminal, or `mtix agent allow dev --yes` for automation. `mtix agent deny dev` never needs a terminal. The beta records and flags harness-session confirmations without refusing them. The doctor checks above show unconfirmed ids and retained source/time/marker audit in operator-local `confirmations.jsonl`; `--fix` never grants permission. Empty boards log `skipped_no_node` instead of creating a task. There is no sender allowlist in this beta: share a hub only with trusted principals. Allow may precede registration: doctor counts active pending ids and prints their exact deny commands; a matching local registration activates the existing grant, while a hub preconfirmation still needs matching known hub identity. Uncommitted allows remain held. Use `mtix agent permissions recover` to list stuck batches and `mtix agent permissions recover --cancel <batch-id>` to cancel with audit; accepted denies and committed grants survive, and cancelled caller ids cannot retry. A new deny quarantines older unfinished allows instead of waiting on publication. Legacy allows without committed preimages remain quarantine holds after cancellation; registration and file requests cannot clear them. Doctor and recovery list these holds; only a fresh operator allow in the matching board clears one. Setup commands remain future work.

## File relay (experimental, opt-in)

A publisher killed after it appended records but before its cursor moved resumes on restart with no operator action: it checks the records past its cursor against its journal, moves the cursor over them without republishing, and refuses with `RELAY_PEER_ID_CONFLICT` when the medium is behind the cursor, when the gap is over 4096 records, when the records are not a contiguous run, or when their content is not its next journal events. A failure to read the journal or to verify the records is not a conflict: it is reported with its own cause and retries on the next tick (run `mtix sync doctor` if it persists). After a publisher crash or restart leaves a torn tail in a sealed segment, the reader applies every complete record once, never a partial one, and logs `reconciled torn seal` when the next segment of the same peer and publisher epoch resumes at or before the first missing record and its first record verifies. It then continues with no operator action. A torn tail the successor does not explain, and any damage inside a sealed segment, still stalls that peer with `RELAY_SEGMENT_CORRUPT` (it is never skipped).

The file relay carries sync events through a shared directory (a mounted folder, a network filer, removable media) for machines that cannot reach a database. It is **experimental**: supported for trial use, its behavior and on-disk format may change in 0.6.0, and it is not yet covered by the release gate. It is **opt-in**: nothing changes unless `sync.relay.dir` is set, and no relay command contacts a hub. The full runbook is the `mtix-sync` skill.

- **Use it** only when the user has asked for a shared-directory transport. Never turn it on to fix an unrelated problem.
- On a gateway, the next hub push sends newly ingested relay events with their original IDs. If a push fails, retry it. The hub accepts each event once. Events the gateway pulled from the hub can travel over the relay without being queued back to the hub. A relay peer that took a task number the gateway already holds is refused at ingest and kept in the relay quarantine (settle it with `mtix sync quarantine resolve`, as the troubleshooting table's relay quarantine row says), never queued for the hub. If the hub later holds the number of a relay-carried task (one ingested from a relay peer, or already published by this peer) for another task, the creation is held, not renumbered, because the relay cannot move its author to the hub's number: `mtix sync doctor` fails `held push events` for it. The hold is permanent (relay-carried tasks are never renumbered), and the hub's task holding that number does not reach relay-only peers while it stands. No command in this build clears it: do not edit the held task or its subtree, because pushing more edits to them only adds held events, and escalate to the operator. `mtix sync doctor` prints this, also under `--json`. A matching hub copy of a relay event retires its forward, also when a quarantined pull is retried.
- **Routine** on a relay peer: `mtix sync relay tick` publishes this peer's events and ingests the others' in one pass. Run it at session start and session end, and whenever you need to exchange work. `mtix daemon` runs the same pass every `sync.relay.poll_interval` seconds (default 5, `0` means tick-only).
- **Verify** with `mtix sync doctor` (the `relay configured` row is the first check; a failing row prints a `fix:` line where one exists, otherwise the error alone, which you report to the user) and `mtix sync relay status --json`. The goal is a run with no FAIL.
- If relay metadata reports `RELAY_META_CORRUPT` at `key_epochs[i]`, entry `i` (counting from zero) repeats or precedes the previous epoch. The error names the cause (`key_epochs not strictly increasing`) and the two epochs. While `relay.json` is refused, relay data flow stops on every attached peer (tick, attach, rotate-key and `mtix sync doctor` all report it); each store keeps its events. `mtix` never repairs the file. Ask the user, then restore `relay.json` in the relay directory from a known-good copy of the relay medium (a backup, or the copy another peer holds) with its `key_epochs` history intact. Never sort, delete or edit `key_epochs` entries: that rewrites rotation history readers have already crossed. Then run `mtix sync doctor` to verify and `mtix sync relay tick` to resume.
- If clone reports a malformed snapshot peer id, ask a current peer to export a fresh snapshot and retry the clone. If clone still names the same snapshot, stop and give the filename and error to the relay maintainer. Clone selects the filename that sorts last.
- **Never** read, print, paste or commit a relay key: the key files live under `.mtix/relay/keys/` with mode 0600, and the user copies them between peers out of band, never through the relay directory. **Never** edit, delete or hand-copy files inside the relay directory, share one `.mtix` between machines, or run `reset-peer`, `retire-peer`, `rotate-key` or `republish` unless the user asked for that recovery: the `mtix-sync` skill says when.
