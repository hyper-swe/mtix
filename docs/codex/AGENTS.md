# AGENTS.md — mtix Integration

The project briefing is root `MTIX.md`, fully regenerated by `mtix docs generate`. Native root `CLAUDE.md` and `AGENTS.md` contain mtix pointers alongside user content. Valid mtix marker blocks migrate without changing other user bytes; malformed pairs are refused. `HYPERSWE.md` suppresses new pointers and absent native-file creation, while existing pointers remain. Reference files in `.mtix/docs/` keep their existing `--force` behavior. `MTIX.md` defaults to tracked. Every generation run checks all existing root `CLAUDE.md` and `AGENTS.md` files, including unchanged pointers. If all are ignored or locally excluded, mtix adds one marked block (`# mtix: managed local briefing` followed by `/MTIX.md`) to Git’s local `info/exclude`, including Git worktrees. Any tracked or otherwise non-ignored pointer, or no pointer files, removes only that mtix-owned block. All user and unmarked exclude rules survive byte-for-byte, including a missing final newline. If a user rule still ignores `MTIX.md` when a pointer is tracked, generation prints a one-line notice. No Git repository means no exclude write. The committed `.gitignore` is never edited for `MTIX.md`.

Nonempty agent IDs and assignees must fit in 64 UTF-8 bytes and must not be whitespace-only or contain control or invisible format characters (including bidi controls and zero-width characters). Accepted raw values are preserved unchanged. An empty create assignee means no explicit assignment: parent auto-claim still applies when enabled. A present empty update assignee clears the assignment; omission preserves it. Claim requires an agent ID. Unclaim acts as the given agent. The CLI uses `--agent`, else `MTIX_AUTHOR_ID`, else the `author_id` config key; MCP uses `agent_id`, with the same fallbacks; REST requires the `X-Agent-ID` header and returns 400 without it; gRPC has no fallback and needs the agent in the request. It is refused when no agent is set. Only the assignee can release a claim unless force is given. This check is a coordination guard on a self-asserted identity (any caller can name the assignee), not authorization. These checks apply to existing CLI, REST, gRPC and MCP inputs; they do not rewrite historical imported or synchronized identities.

mtix is an AI-native micro issue manager. It provides hierarchical task
decomposition with dot-notation context chains for LLM agents.

## Setup

```bash
# Install mtix (choose one)
brew install hyper-swe/tap/mtix
# or download from https://github.com/hyper-swe/mtix/releases

# Initialize in your project
cd /path/to/your/project
mtix init --prefix PROJ
```

## Task Workflow

### 1. Find Work

```bash
mtix ready              # List tasks available for pickup
mtix list --status open  # All open tasks
```

### 2. Read Context

```bash
mtix context PROJ-1.2.3  # Assembled briefing from root to this task
```

The context chain traverses from root to leaf, combining every ancestor's
description into a single prompt. This is your complete briefing — read it
fully before starting.

### 3. Claim and Execute

```bash
mtix claim PROJ-1.2.3 --agent codex
# ... do the work ...
mtix done PROJ-1.2.3
```

### 4. Create Tasks for New Work

Every change needs a task — even one-line fixes:

```bash
mtix create "Fix null validation in CreateNode" \
  --description "Why this task exists" \
  --prompt "Exact files and functions to modify" \
  --acceptance "Testable criteria that define done"
```

`mtix create --type` and `mtix update --type` set work classification (bug, feature, task, chore, refactor, test, doc). Update omission preserves; `--type=` clears. `mtix list --type` filters hierarchy (epic, story, issue, micro); `mtix list --issue-type` filters work classification. Existing unclassified nodes remain unset.

### 5. Decompose Large Tasks

```bash
mtix create "Subtask title" --under PROJ-1 \
  --description "..." --prompt "..." --acceptance "..."
```

### 6. Export State

```bash
mtix export  # Export task state to .mtix/tasks.json
```

## Rules

1. **Always read the context chain** before starting work (`mtix context <id>`)
2. **Never skip task creation** — every change must be tracked
3. **Report blockers** with `mtix comment <id> "blocked: reason"`
4. **Run `mtix export`** before committing — include tasks.json in your commit

## Waiting for inbox events

An optional background park is `mtix inbox --agent <agent-id> --wait --timeout 0`:
zero has no limit, and already pending events return even if the initial
database lookup outlasts a positive timeout. That lookup remains interruptible
by caller cancellation (CLI SIGINT or SIGTERM). After an empty lookup, waiting
for new events uses only the remaining timeout budget measured from entry.
Events mean exit 0; an empty positive timeout means exit 5; SIGINT or SIGTERM
means exit 7.
A negative timeout is refused. Keep foreground waits within the harness's tool
limits; use an indefinite park only where background tasks are supported. Handle
and ack events explicitly before parking again.

For MCP `mtix_inbox_wait`, explicit `timeout_seconds=0` waits without a limit
until an event or caller cancellation. Omission uses default 60 seconds;
positive values are capped at 60 seconds, and negative values are refused.
Cancellation is an error, and an empty positive timeout returns `[]`.

## MCP Integration

mtix includes an MCP server for direct tool access:

```bash
mtix mcp -C /path/to/project
```

This provides 36+ tools for task management, agent coordination,

## Health diagnostics

Plain `mtix doctor` preserves operator-local files, including stale attach shims
and records. Use `--fix` for registered shim and glue repairs;
other commands retain automatic attach refresh.

## Trust and grants

Registered local-only ids are implicitly wakeable unless denied. Hub or relay ids require operator-local confirmation: `mtix agent allow dev` needs a terminal, or use `mtix agent allow dev --yes` for automation. `mtix agent deny dev` never needs a terminal. Allow can precede registration; doctor counts current pending ids and prints exact revoke commands. Registration here activates a preconfirmation without another confirmation, while hub preconfirmations need matching known hub identity. The beta accepts and flags harness confirmations and records marker names without values. `mtix doctor --json` shows held ids and retained source/time/mode audit in protected operator-local `confirmations.jsonl`; `--fix` never grants permission. Empty boards record `skipped_no_node`. Share a hub only with trusted principals; this beta has no sender allowlist. Uncommitted allows remain held. Use `mtix agent permissions recover` to list stuck batches and `mtix agent permissions recover --cancel <batch-id>` to cancel with audit; accepted denies and committed grants survive, and cancelled caller ids cannot retry. A new deny quarantines older unfinished allows instead of waiting on publication. Legacy allows without committed preimages remain quarantine holds after cancellation; registration and file requests cannot clear them. Doctor and recovery list these holds; only a fresh operator allow in the matching board clears one. Setup remains future work.

## File relay (experimental, opt-in)

The file relay carries sync events through a shared directory (a mounted folder, a network filer, removable media) for machines that cannot reach a database. It is **experimental**: supported for trial use, its behavior and on-disk format may change in 0.6.0, and it is not yet covered by the release gate. It is **opt-in**: nothing changes unless `sync.relay.dir` is set, and no relay command contacts a hub. The full runbook is the `mtix-sync` skill.

- **Use it** only when the user has asked for a shared-directory transport. Never turn it on to fix an unrelated problem.
- **Routine** on a relay peer: `mtix sync relay tick` publishes this peer's events and ingests the others' in one pass. Run it at session start and session end, and whenever you need to exchange work. `mtix daemon` runs the same pass every `sync.relay.poll_interval` seconds (default 5, `0` means tick-only).
- **Verify** with `mtix sync doctor` (the `relay configured` row is the first check; a failing row prints a `fix:` line where one exists, otherwise the error alone, which you report to the user) and `mtix sync relay status --json`. The goal is a run with no FAIL.
- **Never** read, print, paste or commit a relay key: the key files live under `.mtix/relay/keys/` with mode 0600, and the user copies them between peers out of band, never through the relay directory. **Never** edit, delete or hand-copy files inside the relay directory, share one `.mtix` between machines, or run `reset-peer`, `retire-peer`, `rotate-key` or `republish` unless the user asked for that recovery: the `mtix-sync` skill says when.
